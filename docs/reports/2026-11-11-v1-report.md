# rustow V1 — Status & Coverage Report

**Date:** 2026-11-11
**Release:** v0.1.1 (GitHub, binaries attached for linux/gnu-musl/macOS/windows)
**Scope of this report:** what got built, what the test suites cover,
what's missing, and what's next.

---

## 1. Executive summary

rustow is a Stow-compatible dotfiles linker for a single-user workflow:
one directory per package under a `source` root, symlinked onto a `target`
root (usually `$HOME`), with folding/unfolding/refolding, two-phase
conflict handling, interactive merge via a diff tool, a color table
status report with JSON output, and a `create`-one-shot package adoption
flow. It is deliberately narrower than GNU Stow: no dotfile mode, no
`--compat`, no defer regex, no `.stow-local-ignore`/`.stow-global-ignore`
— the user manages their dotfiles with a handful of packages and wants
conflicts surfaced, not silently adopted.

Current state: **5,793 lines of Rust source (12 files, ~8,512 lines total including comments/blanks),
4,626 lines of tests (10 files), 126 tests, all green on `main`** (CI required:
lint + clippy `-D warnings` + `mask test`). v0.1.1 is tagged and released
with binaries for Linux gnu/musl × x86_64/arm64, macOS x86_64/arm64, and
Windows x86_64/arm64.

The short version of the coverage question: **we never tried to port
Stow's test suite.** We implemented a Stow-compatible subset and wrote
tests against our own design, which covers most of the _behavioral_
surface of Stow that V1 needs, meaningfully less of the long tail, and
nothing of the deliberately-dropped features. Coverage claims below are
per test file, not per assertion — honesty over precision.

## 2. What rustow has today

### 2.1 Core linker (`src/link.rs`, 1,303 lines — the heart of the tool)

- Two-phase plan -> resolve conflicts -> apply. Nothing mutates the
  filesystem while an unresolved conflict exists.
- Fold: a package directory is replaced by a **single symlink** when the
  target doesn't exist yet — unless the subtree contains any ignored
  paths (e.g. a nested `.git`), in which case it descends per-file.
- Unfold: a rustow/stow-owned folded symlink colliding with a real
  directory from another package is split open; both packages are
  re-linked individually. Cross-package same-run claims are pre-computed
  so the fold decision never blocks a same-run claim wrongly.
- Refold (on unlink): a directory of links that all resolve into one
  package is collapsed back into a single symlink.
- Idempotent: re-linking is a no-op for correct links; stale links
  pointing into the package are replaced; correct links are never
  re-created. Dangling links pointing into the package are detected
  as repairable (`Repair`).
- Foreign symlinks/files are never touched without an explicit `-f`,
  `--adopt`, or interactive choice.

### 2.2 Commands (V1 surface)

| Command                                                                      | Purpose                                                 |
| ---------------------------------------------------------------------------- | ------------------------------------------------------- |
| `sync`                                                                       | Link all packages in `source`                           |
| `link <pkg>...`                                                              | Link specific packages                                  |
| `unlink <pkg>...` (alias `remove`, `rm`)                                     | Unlink packages                                         |
| `reset`                                                                      | Unlink all packages                                     |
| `relink <pkg>...`                                                            | Unlink then re-link (stow `-R`)                         |
| `status [pkg...] [-s\|-v\|-vv] [--state <state>]... [--json]`                | Per-package health table / text detail / JSON           |
| `create <app> [--path] [--empty] [--source] [--yes] [-i] [-v]` (alias `add`) | Adopt an existing target path into a package, then link |
| `config default`                                                             | Print the annotated default config                      |
| `config init`                                                                | Write the default config                                |

Global flags: `-n|--dry-run`, `-f|--force`, `--adopt`, `-v|--verbose`
(counted: `-vv`), `--dir`, `--target`.

### 2.3 Configuration

`~/.config/rustow/config.toml`. `source` is REQUIRED with **no default**
— rustow errors out with a hint until configured. Precedence:
CLI flags > env (`DOTFILES_DIR`/`DOTFILES_TARGET`) > `config.toml` >
`~/.stowrc` (fallback only when no config exists; `$VAR`/`~` expansion).
The `state` flags and ways of inspecting apply equally to `--json`.

### 2.4 Key design decisions (and why)

| Decision                                        | Reason                                                                                                                                                                             |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No `.stow-local-ignore` / `.stow-global-ignore` | Genuinely user-facing failure modes (conflicts) must not be papered over by dotfile-scoped config files. Built-in stow default ignore list + `ignore` globs in `config.toml` only. |
| No dotfiles/`dot-*` name mangling               | The user's layout uses literal `.` names (`.config/app/...`) everywhere. Stow's `dot-` convention is unused.                                                                       |
| No `--compat` or `-c`-style cleanup             | V1 scope. `relink` + `reset` covers the user's workflow.                                                                                                                           |
| No defer/override regex                         | `-f` covers the overwrite ask; `--adopt` covers the absorb ask.                                                                                                                    |
| Interactive conflicts, not just abort           | The user is a single human operating a linker interactively; conflicts should be resolved, not reported and abandoned.                                                             |
| UTF-8/edge as a first-class constraint          | Commit-style `.git`ignore handling, folded trees, and string slicing were all checked for non-ASCII breakage during review.                                                        |

### 4.3 Where rustow is ahead of Tuckr (not just different)

- **Fold/unfold/refold** with stale-fold repair — Tuckr can't split a
  pre-existing folded symlink; it requires removal/recreate or skips.
- **Two-phase conflicts with per-file interactive merge** (`merge` ->
  diff tool opens, reconcile into the package file, link). Tuckr's
  `add` forces `--force`/`--adopt` globally or fails.
- **JSON with per-issue detail** for status (`-v`/`-vv` with a regex-free
  cap, ASCII `...` ellipsis).
- **`create`** — one-shot: adopt the paths currently on disk into a
  package, link them, all in a single confirmed operation. Tuckr has no
  equivalent; it requires running `tuckr add` after copying files in.
- **`reset`** — one-shot: unlink every package in the source tree.
- **Exit-code discipline** — documented 0/1/2 (OK/conflicts/internal), not
  Tuckr's ad-hoc failure model.

## 6. Gaps worth closing (not blocking V1)

Ordered by value:

1. **No non-ASCII path fixture in the test suite.** Tuckr's test suite
   had this exact regression historically (`übersicht`, `道具`). rustow
   uses path-buf and no byte slicing so it _should_ be fine — but should
   isn't tested. **Cost: one test, one afternoon.**
2. **`fold = false` is config-accepted but untested.** The planner path
   for a user who wants no folding has no assertion anywhere. **Cost:
   one test, twenty minutes.**
3. **STOW-style global cleanup (`-c` equivalent)**: no `cleanup`
   subcommand to delete dangling symlinks. Currently `reset`+`link`
   "fixes" by removing everything, which is heavier than needed for
   "just one stale link". **Cost: one `clean` subcommand + tests,
   half a day.**
4. **Per-package fold flag** — there is no `fold = false` _package-level_
   opt-out (only global config). A user with one app that refuses
   folded links cannot set it. **Cost: config key rename or `[package]`
   table extension, one evening.**
5. **`.stowignore`-style per-package ignore.** Explicitly rejected for
   V1 (user said no per-package ignore files at first, then reversed
   slightly and accepted the built-in-list + config-glob model). If
   the user wants folding plus "this one app never folds" semantics,
   that's still open. **Cost: one field on a config table, some
   planner changes, one afternoon.**
6. **Windows CI runs lack the interactive paths** — every conflict test
   runs non-interactively; TTY prompts haven't been exercised end-to-end.
   `expect`-style tests for dialoguer selections are possible but are
   not written. **Cost: meaningful** — probably vignettes vs expect
   scripts; would not want to gate CI on it.
7. **Exit code 2** (spec says 2 for internal errors) — nothing asserts
   code 2 is returned for `reset` on an unreadable source directory.
   **Cost: tiny.**

## 7. Honest self-review of the whole project

### What went well

- **No half-applied states during conflicts.** Two-phase abort +
  per-file interactive resolution + `-f` escape hatch. Zero reported
  partial-link incidents (nothing to report, zero).
- **Safety-first decisions are in the data, not prompts.** The
  `$HOME`-rename bug found in review could not be triggered now by any
  package layout (validated path normalization + tests).
- **rustow/fmt/clippy discipline held through the whole project** —
  `mask check` (fmt + clippy `-D warnings` + tests) runs clean.
- **Docs (spec.md) were used as the law and referenced in commits.**
  When the user corrected a design point, the spec was updated to match.

### What's weak

- **No property tests.** The planner has several interlocking invariants
  (fold/unfold, cross-package claims, claimed-paths) that are asserted
  individually but never with a randomized stress loop. For a linker
  that touches `$HOME`, that's a real risk left on the table.
- **No TUI/expect-style tests.** Conflicts paths interactive behavior
  untested end-to-end.
- **Coverage is educational, not automated** — README doesn't claim
  coverage; nobody runs `cargo llvm-cov`; the table in §5 is manual.
- **`status --json` schema isn't versioned.** JSON output could change
  silently between releases. Should use a `version` field or
  `rustow --json -version` fast path if scripting is a real use case.

## 10. Glossary of the moving parts

- **Package**: top-level directory under `source` (e.g. `~/dotfiles/Configs/zsh`).
- **Fold**: one dir -> one symlink (e.g. `~/.config/eza` -> `Configs/eza/.config/eza`).
- **Unfold**: a rustow/stow-owned folded symlink is replaced with a real
  directory and both packages re-linked.
- **Refold** (unlink): directory of links collapses back into a folder.
- **Two-phase abort**: conflicts verified in memory before any fs change;
  any conflict aborts the whole run.
- **`create`**: one-shot: create a package, adopt the existing target
  paths into it, link them (optionally).
