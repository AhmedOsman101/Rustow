# rustow — Status & Coverage Report

- **Date:** 2026-11-20
- **Release:** v0.1.1 is tagged and published (binaries for linux gnu/musl × x86_64/arm64, macOS ×2, Windows ×2). The v0.2.0 line is complete on its branch and awaiting release; this report reflects that line.
- **Scope:** what exists, what is tested, what is missing, and what is next — written for someone who has not read GNU Stow's manual or Tuckr's source.

---

## 1. If you read nothing else

- rustow is a **dotfiles linker**: it creates symlinks from a "package" directory (your config files, grouped per app) into your home directory. It is not a package manager, not a dotfile framework, not a profile switcher.
- It is **Stow-compatible** in the parts that matter for linking and unlinking: same concept of packages, same fold/unfold/refold behavior, same conflict safety (plan first, change nothing on conflict), same stowrc fallback for people migrating off GNU Stow.
- It is deliberately **much narrower** than Stow: no dotfile-name mangling, no defer/override regexes, no compat mode, no local ignore files, no profiles, no hooks, no secrets. System-path placement is now supported through per-package root mapping and elevation.
- Test suite: **265 passed, 0 failed, 1 ignored; 0 doc-tests** (verified 2026-11-20), plus an end-to-end scenario script run inside a Void Linux container, all scenarios passing. CI enforces lint + clippy + tests on every push and PR.
- One test is ignored because of a known relink-abort bug: when a conflict appears after the unlink phase, links can be removed before the abort prompt is shown. The fix is to restore links before resolving that prompt.
- The rest of this document explains what all of that means, and where the remaining gaps are.

## 2. Primer: what Stow and Tuckr are, and where rustow sits

**GNU Stow** is a small Perl program that has been the reference tool for dotfile symlinking for ~30 years. You keep each app's config files in a directory ("package", e.g. `Configs/zsh/`), and Stow creates symlinks from the target tree (usually `$HOME`) back into the package. The hard parts are:

- **Tree folding** — instead of creating dozens of links under `~/.config/eza/`, Stow creates ONE symlink `~/.config/eza -> Configs/eza/.config/eza`. Faster, cleaner, fewer links.
- **Unfolding** — if another package suddenly needs to own one file inside that folded directory, Stow splits the fold symlink back into a real directory and links each file individually.
- **Conflict detection** — if `~/.zshrc` already exists as a real file, Stow stops and does nothing rather than overwriting it. (Modern Stow ≥2.0 plans everything before touching the disk.)
- **Unstowing** — deleting the links a package created.

**Tuckr** is a newer Rust rewrite of the same idea, with extra machinery on top: host-specific "profiles", conditional deployment per OS, pre/post-deploy hooks, secret management, and a TUI-ish add flow. If you want a dotfiles _framework_, that is the bigger tool.

**rustow** is a narrow, safe Stow-compatible linker in Rust. It keeps the parts above that are universal (folding, refolding, conflicts-never-silently-overwritten, stowrc migration compat) and leaves out both Stow's vintage baggage (dot-name mangling, compat mode, regex conflict policy) and Tuckr's framework scope (profiles, hooks, secrets). It adds one capability neither has in the same shape: per-package placement of selected paths at absolute system locations, applied through elevation.

### Vocabulary, in plain words

- **Package** — a top-level directory under your `source` root holding one app's files, e.g. `Configs/zsh/`.
- **Source directory** — the root of all packages (`Configs/`). rustow calls this `--dir` / `DOTFILES_DIR` / `source`.
- **Target directory** — where links are created, usually `$HOME`. `--target` / `DOTFILES_TARGET` / `target`.
- **Linking** — creating symlinks in the target pointing into the package. **Unlinking** — deleting only the links that package created.
- **Fold** — replacing a would-be tree of links with a single symlink (see above). A directory is folded only when the target has no real directory there and nothing ignored (like a nested `.git`) lives inside the subtree.
- **Unfold** — splitting a rustow/stow-owned fold link into a real directory so two packages can coexist under it.
- **Refold** — after unlinking, collapsing a directory that now holds only links into one package back into a single fold symlink.
- **Conflict** — the target path is occupied by something rustow would have to replace: a real file, a real directory, or a symlink pointing into a different package. rustow never resolves one implicitly; either you pick an action (overwrite / adopt / skip / interactive merge) or the whole run aborts before any file is created or deleted.
- **Adopt** (`--adopt`) — move the existing target file _into_ the package, then link. (stow `--adopt`.)
- **Dry run** (`-n`) — print what would happen, change nothing.
- **Two-phase plan** — rustow first computes every action and every conflict in memory; if any conflict is unresolved, ZERO filesystem changes happen. No half-applied states.
- **Ownership** — a symlink is "rustow-owned" if it resolves into the configured `source` tree. Foreign links are never removed without an explicit flag.
- **Provenance** — where the effective config came from (CLI flag / env var / config file / stowrc), tracked so rustow can explain itself on startup.
- **`clean`** — deleting rustow-owned symlinks whose _destination no longer exists_ (the equivalent of `stow -c`). Distinct from unlink: unlink removes a package's links unconditionally; clean removes only broken ones, and works even if the package was deleted entirely.
- **`fold_ignore`** — config list of package names that must never be folded (they get per-file links while everything else folds as usual).
- **`includes`** — a per-package, biome-style list layered over the global ignore rules. Positive entries re-include paths the global list hid; `!`-prefixed entries hide them again. It affects only that package, and paths it hides also block folding. See [ADR 0002](../adr/0002-per-package-includes.md).
- **Root mapping** — a per-package config table that places a package path at an absolute destination outside the target tree (e.g. under `/etc`). Root-mapped actions are excluded from folding and applied through elevation. See [ADR 0001](../adr/0001-root-targeting.md).
- **Elevation** — running only the root-mapped actions with elevated privileges (probing `sudo`, then `doas`, overridable with `elevate_cmd`); the rest of the run stays with the invoking user.
- **`config migrate`** — a one-shot command that copies unset values from `~/.stowrc` into `config.toml` without deleting the stowrc. See [ADR 0004](../adr/0004-config-migrate.md).
- **Ignored paths** — rustow ships Stow's default ignore list (`.git`, editor backups, etc.) plus your own `ignore` globs in `config.toml`. Ignored paths block folding (so nested `.git` directories are never swallowed into a fold) and are never linked.

## 3. What changed since the last report

The earlier report covered the v0.1.1 line, which introduced `clean`, `fold_ignore`, the `--no-stowrc` kill switch, and the `source == target` refusal. Those remain. This section lists what the v0.2.0 line adds.

- **Verified review fixes.** Findings from the whole-tree review were reproduced before any code changed, then fixed where they reproduced. `clean` no longer descends into the source tree, even when the source lives under the target, and honours ignore rules. `relink` plans its link phase before unlinking, so a conflict discovered up front leaves the tree untouched. `create` refuses to adopt a path already managed by another package, including through an explicit source argument. `status` rejects a fold that points at the wrong subtree and reports file/directory kind mismatches as conflicts instead of a misleading "unlinked". The generated config points at the canonical repository, and stowrc escape sequences decode by code point so non-ASCII paths round-trip. One reported finding (provenance misattribution of a CLI override) did not reproduce and needed no change.
- **Exit-code contract.** Exit codes now follow [ADR 0003](../adr/0003-exit-codes.md): `0` success, `1` general failure (including declining an interactive prompt), `2` usage error from the argument parser. The contract is documented and pinned by tests; the old, unverified "2 = user aborted" meaning is gone.
- **Per-package `includes`** — a per-package ignore/inclusion list layered over the global rules, driving both linking and fold demotion. See [ADR 0002](../adr/0002-per-package-includes.md).
- **Root targeting and elevation** — package paths can be mapped to absolute destinations outside the target, with plan-time preflight, a single authorization prompt or `--as-root`, and status/unlink/clean wiring. See [ADR 0001](../adr/0001-root-targeting.md).
- **`rustow config migrate`** — graduates a stowrc into `config.toml`, writing only values the config leaves unset, with a matching offer during `config init`. See [ADR 0004](../adr/0004-config-migrate.md).
- **Versioned JSON output** — `status --json` carries a top-level `version: 1`. See [ADR 0005](../adr/0005-json-version.md).
- **Test investment** — property-based invariant tests for the planner, a pseudoterminal harness driving the interactive conflict prompt, and pinned verbose-output formats for link/unlink/clean/create.
- **Recorded decisions** — husky-rs remains a regular dependency and why ([ADR 0006](../adr/0006-husky-rs.md)); Windows is positioned as a Unix-like-only environment ([ADR 0007](../adr/0007-distribution.md)); profiles, host-conditional deployment and templating are future work ([ADR 0008](../adr/0008-profiles-future.md)).
- Test count went 149 → **265 passed** (plus one ignored test).

## 4. What rustow covers today (by capability, not by file)

For each capability: what it does, and how it is exercised in tests. "Tested" means a named behavior has at least one assertion, either through the real binary against isolated temporary homes or at the plan layer; both are first-class.

### 4.1 Linking and folding

- `rustow sync` links every package; `rustow link <pkg>...` links selected ones. Tested through the CLI and in the container scenario.
- Tree folding: a package whose target subtree doesn't exist yet gets one symlink for the whole directory. Tested (fold creation, demotion when the subtree contains ignored paths, stale-fold replacement).
- Unfold: a rustow-owned fold link colliding with another package's real directory is split into a real directory and both packages are re-linked. Tested.
- Refold: unlinking a directory that now contains only links into one package collapses it back into a fold symlink. Tested, including respect for per-package `includes`.
- Cross-package same-run claims are pre-computed so fold decisions don't misfire. Tested.
- `fold = false` (global) forces per-file links; `fold_ignore = [...]` opts specific packages out; `includes` hides specific paths for one package only. All tested, including a package whose effective list hides everything (a clean no-op that `status` reports as unlinked).
- Re-linking is idempotent; dangling links pointing back into the package are repaired. Tested (also as randomized properties).
- Packages containing only ignored paths are a clean no-op. Tested.
- Foreign symlinks and real files are never silently replaced; `-f` and `--adopt` are the two explicit escape hatches. Tested.

### 4.2 Unlinking

- `unlink <pkg>...` (aliases `remove`, `rm`) removes only that package's links; unrelated real files and foreign links in the same tree are left alone. Tested, including foreign-symlink preservation.
- `reset` unlinks everything; `relink` unlinks then re-links. Both tested end-to-end. A conflict found before relinking now aborts without removing anything.
- Unlink of a package that was never linked, or is empty, is a successful no-op. Tested.
- `clean` deletes only broken rustow-owned links. Tested (live links untouched, dry-run, foreign-broken links kept, fold links whose package vanished, idempotency). It never descends into the source tree and honours ignore rules. Root-mapped links are cleaned through elevation like any other owned link.

### 4.3 Conflict handling

- Detected before any mutation: real file at target, real directory at target, symlink to another package, symlink to nowhere-into-the-package, wrong-package links, dir-vs-file shape mismatches, and folds pointing at the wrong subtree. All abort the entire run when unresolved. Tested at plan and CLI level, including as randomized properties asserting that an unresolved conflict changes nothing.
- Resolution paths: interactive prompt on a TTY (skip / overwrite / adopt / interactive merge in a diff tool), `-f` to overwrite everything, `--adopt` to absorb everything, non-TTY without a flag → abort with a full report and zero changes. Tested for every non-interactive path.
- The interactive prompt now has automated coverage under a pseudoterminal: choosing overwrite replaces the file with a link, and choosing skip leaves the file in place. A third case — aborting a relink that has already unlinked — is ignored pending the known fix described in §1.

### 4.4 Adopting existing files

- `create <app>` (alias `add`) moves existing target paths into a new package and links them, in one confirmed operation. Handles `--source` (custom path), `--path` (package-relative destination), `--empty`, `--yes` (non-interactive), absolute/traversal path rejection, cross-filesystem moves, and refuses to touch an existing package's contents without confirmation. Tested.
- Adoption refuses any source path that lies inside the source tree, so an existing package's files cannot be relocated into a new one by accident. Tested for both the default and explicit-source routes.

### 4.5 Status and observability

- `status [pkg]...` reports per-package `linked` / `partial` / `unlinked` / `conflict` with a table, `-s` summary mode, `-v`/`-vv` per-issue detail (line-capped; `-vv` uncaps), `--state` filtering (repeatable, also applies to JSON), and `--json` machine-readable output. Tested, including exit codes (0 iff every inspected package is fully linked) and `--json` parseability.
- `status --json` emits a top-level `version: 1` alongside `packages` and `summary`, so scripts can pin against the shape. See [ADR 0005](../adr/0005-json-version.md). Tested.
- A package with a root mapping shows a `root` note in its status row. Tested.

### 4.6 Configuration and provenance

- `~/.config/rustow/config.toml`: `source` (**required, no default** — rustow refuses to guess), `target` (default `$HOME`), `fold`, `fold_ignore`, `ignore`, `diff_tool`, `verbose`, plus the per-package `includes` and `root` tables.
- Precedence: CLI flags > environment (`DOTFILES_DIR`, `DOTFILES_TARGET`) > `config.toml` > `~/.stowrc` (fallback only when no config file exists).
- `~/.stowrc` supports `--dir` / `--target` / `--verbose` with stow-compatible expansion: `$HOME`, `${HOME}`, leading `~`, and backslash escapes (`\$`, `\~`) keeping things literal, decoded by code point. stowrc can be disabled outright with `--no-stowrc` or `RUSTOW_NO_STOWRC=1`; when that happens and a stowrc file exists, rustow prints a one-line note instead of silently ignoring it.
- Typos and unknown keys in config warn; unknown stowrc keys warn and are ignored; malformed stowrc lines abort with line numbers. Per-package tables reject unknown keys and wrong types, and malformed `includes` globs are config errors. Tested.
- On a TTY with no config, rustow warns and offers to create one pre-filled from the values in use; `[s]ilence` writes a stamp file; `[a]bort` exits. Non-TTY with no config: a one-line warning on stderr, never a prompt, and the run continues (a conflict needing a decision still aborts the link phase as usual). Tested at the suite level.
- `source == target` is refused. Tested.
- `schema.json` and `docs/config.toml` are mechanically checked against the config model by tests — they cannot drift silently.
- Exit codes (ADR 0003, documented in `docs/spec.md` and pinned by tests): `0` success (for `status`, every inspected package linked and conflict-free); `1` general failure — unresolved conflicts, runtime errors, and declining an interactive prompt; `2` usage error (clap) only for unknown or malformed CLI arguments. Declining a prompt is **not** a distinct code and never returns `2`; stderr names the reason. All three codes are pinned by tests through the real binary. See [ADR 0003](../adr/0003-exit-codes.md).

### 4.7 Root targeting and elevation

- A package can map a package-relative path to an absolute destination outside the target tree with a `[package.<name>.root]` table. Keys cannot escape the package (`..` is rejected); values must be absolute after `~` expansion; trailing slashes are cosmetic. The source path's filesystem type decides the mapping at plan time: a directory source produces one fold-style link at the mapped location, a file source one link at the exact destination. A mapped source that does not exist is a plan-time error.
- Root-mapped paths never fold, never refold, and are excluded from the package's fold decision, but take part in conflict detection and status counting as usual.
- Applying them requires write access the invoking user usually lacks. rustow preflights writability and elevation availability at plan time, then applies only the root-mapped actions through an elevation helper — probing `sudo` then `doas`, overridable with `elevate_cmd` — after a single authorization prompt or with `--as-root`. A dry run applies nothing and elevates nothing. Missing elevation, an unwritable parent, a conflict at an absolute destination, or a declined prompt all abort before any filesystem change.
- `unlink` removes exactly the mapped links and leaves the package's user-home links alone; `clean` removes broken root links through elevation. All of this is tested end to end with an elevation stub. See [ADR 0001](../adr/0001-root-targeting.md).

### 4.8 Migration from Stow

- `rustow config migrate` reads `~/.stowrc` (or an explicit path), prints the adoption diff and writes only the values `config.toml` leaves unset — existing config values always win. `--yes` adopts without prompting; `--dry-run` prints the plan and writes nothing; a malformed or unusable stowrc produces a clean error and leaves the config untouched.
- The stowrc is never deleted or renamed; rustow only notes that it can be removed once a config file exists. `config init` detects a stowrc and offers the same adoption inline. Tested across empty and existing configs, malformed input, dry runs, and the init path. See [ADR 0004](../adr/0004-config-migrate.md).

### 4.9 Distribution

- Tagged releases cut binaries for linux gnu/musl (x86_64, arm64), macOS (x86_64, arm64), Windows (x86_64, arm64) via GitHub Releases. No crates.io.
- `cargo install --path .` works; binary is self-contained (no runtime).
- rustow targets Unix-like systems. On Windows it works under Git Bash / WSL / Cygwin and is not a first-class target; the binaries keep shipping for those environments. See [ADR 0007](../adr/0007-distribution.md).

## 5. What was missing, what is now done, what remains

### 5.1 Previously missing

1. **Property-based planner tests — done.** Randomized trees never panic in plan or apply; dry runs never mutate; linking is idempotent; an unresolved conflict changes nothing; the two-package fold/unfold/refold round-trip holds; and unlink after link restores a fresh target. All green.
2. **TTY interaction tests — done, with one known gap.** A pseudoterminal harness drives the interactive conflict prompt; overwrite and skip are covered automatically. The relink-abort case is ignored because of the bug noted in §1.
3. **`status --json` schema is not versioned — done.** The output now carries a top-level `version: 1`. See [ADR 0005](../adr/0005-json-version.md).
4. **Exit-code semantics — done, and the earlier wording was wrong.** Exit code `2` is for usage errors only (unknown or malformed CLI arguments), not for a user-aborted conflict. Declining a prompt exits `1`, like any other general failure, and that path is now pinned by tests alongside the other codes. See [ADR 0003](../adr/0003-exit-codes.md).
5. **`target` inside `source` (and vice versa) is still not refused.** Only strict equality is refused today. Stow performs the same equality-only check; the broader containment case remains undecided.

### 5.2 Previously partial

1. **Conflict-resolution UX — now covered for the prompt itself.** Non-interactive paths remain exhaustively tested, and the interactive flow has automated pseudoterminal coverage for overwrite and skip. The relink-abort sequence is the one remaining untested path (§1).
2. **Windows — positioned in docs.** rustow is documented as targeting Unix-like systems, with Windows supported through Git Bash / WSL / Cygwin rather than as a first-class target. CI still builds the binaries and exercises behavior on Linux; interactive Windows symlink semantics are not pinned in tests. See [ADR 0007](../adr/0007-distribution.md).
3. **Verbose output for link/unlink commands — done.** Link, unlink, clean, and create verbose output are pinned by assertions on their load-bearing line formats.

## 6. Design decisions and rationale

### 6.1 Cleanup linking

`clean` is exactly the GNU Stow `-c` equivalent: it walks the target tree, finds symlinks rustow owns that now resolve into nothing, and deletes them. Fold links whose package vanished are handled, `-n` gives a dry run, and foreign links — even broken ones outside the source tree — are left alone. It also honours ignore rules and never descends into the source tree, even when the source is nested under the target. No separate compat flag is needed.

### 6.2 Defer and compat

Both are GNU Stow flags; neither exists in rustow.

**`--defer=<regex>`**: skip linking a file whose path matches the regex, if another package already owns it. **`--override=<regex>`** is the opposite: always link matching paths even if another package owns them. rustow has no regex-scoped conflict policy; the equivalents are `-f` (overwrite everything), `--adopt` (absorb everything), or the interactive prompt (decide per conflict). What it does not have is "these specific path classes defer to another package". Recommendation remains no for this line: the use case is narrow, regex conflict policy is a power feature whose misuse silently links or overwrites the wrong things, and if it is ever needed the right shape is a per-package policy in config rather than a raw regex flag.

**`--compat`** (`-p`): when unstowing, scan the whole target tree for orphaned links instead of just the package image. `clean` already does this job more generally — it walks the target independently of any package image and removes every broken rustow-owned link — so a compat flag would be redundant.

### 6.3 Local ignore files

Stow supports `.stow-local-ignore` (per package) and `~/.stow-global-ignore` (user-wide), both regex lists. rustow's answer is the built-in default ignore list, global `ignore` globs in config, per-package `fold_ignore`, and now per-package `includes`, with no hidden dotfiles inside packages; that keeps one decision in one place. `~/.stow-global-ignore` is redundant with the global `ignore` key. If a per-package ignore file is ever genuinely needed, the coherent shape is a per-package config table, not dotfiles peppered through packages.

### 6.4 Disabling stowrc detection

A `config.toml` key cannot disable stowrc detection — by the time a config file exists, stowrc is never consulted, so such a key would be inert. The kill switch therefore lives where it can work with zero config and zero env vars: `--no-stowrc` and `RUSTOW_NO_STOWRC=1`. Either disables detection completely, and when rustow would have read a stowrc but was told not to, it prints a one-line note naming the file instead of silently ignoring it. With no config, no env vars, and stowrc disabled, the usual "source is not set — run `rustow config init`" error appears, exactly as if the stowrc never existed.

### 6.5 Test coverage additions

Alongside the edge cases already covered (non-ASCII paths, global fold opt-out, numeric directory names, unlink no-ops, source/target equality refusal, clean idempotency and fold removal, stowrc kill switch), this line added the higher-investment cases that were previously deferred: randomized planner invariants, an interactive-prompt harness under a pseudoterminal, versioned JSON assertions, pinned verbose formats, and the exit-code contract. Property tests are not treated as out of scope; they are now in place.

## 7. Deliberately out of scope, and why

These are design decisions of the tool, stated so adopters can plan around them.

1. **`dot-` name mangling (`--dotfiles`)**. Stow renames `dot-bashrc` → `.bashrc` so package trees can be browsable without hidden files. rustow links literal trees; package files are exactly what lands in the target. The convention saves nothing in a modern repo layout and doubles the mental model.
2. **Defer/override regexes**. See §6.2. Superseded by `-f`, `--adopt`, interactive resolution, and prospectively a per-path conflict policy in config.
3. **Compat mode**. See §6.2. Superseded by `clean`.
4. **`.stow-local-ignore` / `.stow-global-ignore`**. See §6.3. Redundant with `ignore` globs; a per-package version would be a config table if ever needed.
5. **Profiles, host-conditional deployment, and templating**. rustow manages "this source tree → this target tree, once", with root mapping for absolute system paths. Host switching is a namespace problem with existing solutions; templating breaks the link-never-copy invariant. Both are future work with their own design record. See [ADR 0008](../adr/0008-profiles-future.md).
6. **Hooks (pre/post deploy)**. Deploy automation belongs to your actual deploy pipeline, not a linker. Combining them makes failures un-debuggable ("did the link or the hook fail?").
7. **Secrets / encryption**. Different category of tool problem (key management, rotation); using a linker to deliver secrets conflates the threat models.
8. **`stow -c`-adjacent archive modes, `from-stow`**. Migration is a one-shot manual affair, now eased by `config migrate`; supporting bulk converters is feature debt with no steady-state payoff.

## 10. Glossary (for stow refugees and newcomers alike)

- **Package** — one app's directory of config files inside your source tree.
- **Source tree** — the directory holding all packages. **Target tree** — where links go (usually `$HOME`).
- **Fold** — one directory → one symlink. **Unfold** — split that symlink back into a real directory. **Refold** — collapse a links-only directory back into a symlink.
- **Two-phase** — everything planned in memory before anything touches disk; unresolved conflicts abort the whole run.
- **Conflict** — target occupied by something rustow must not silently replace.
- **Adopt** — move the target file into the package, then link it.
- **`clean`** — remove broken rustow-owned symlinks (`stow -c`).
- **Provenance** — which config layer supplied the settings in effect.
- **`fold_ignore`** — packages that never fold.
- **`includes`** — a per-package list that re-includes or hides specific paths over the global ignore rules.
- **Root mapping** — a per-package table placing a path at an absolute destination outside the target, applied with elevation.
- **`config migrate`** — copy unset stowrc values into `config.toml` in one command.
- **Idempotent** — running link twice changes nothing the second time.
