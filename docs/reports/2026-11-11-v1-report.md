# rustow — Status & Coverage Report

**Date:** 2026-11-13
**Release:** v0.1.1 is tagged and published (binaries for linux gnu/musl × x86_64/arm64, macOS ×2, Windows ×2).
Unreleased on `main` since v0.1.1: `clean`, `fold_ignore`, `--no-stowrc` / `RUSTOW_NO_STOWRC`, the `source == target` refusal, and 11 new edge-case tests.
**Scope:** what exists, what is tested, what is missing, and what is next — written for someone who has not read GNU Stow's manual or Tuckr's source.

---

## 1. If you read nothing else

- rustow is a **dotfiles linker**: it creates symlinks from a "package" directory (your config files, grouped per app) into your home directory. It is not a package manager, not a dotfile framework, not a profile switcher.
- It is **Stow-compatible** in the parts that matter for linking and unlinking: same concept of packages, same fold/unfold/refold behavior, same conflict safety (plan first, change nothing on conflict), same `~/.stowrc` fallback for people migrating off GNU Stow.
- It is deliberately **much narrower** than Stow: no dotfile-name mangling, no defer/override regexes, no compat mode, no `.stow-local-ignore`/`.stow-global-ignore` files, no profiles, no hooks, no secrets.
- Test suite: **149 tests, all green** (verified 2026-11-13), plus an end-to-end scenario script run inside a Void Linux container. CI enforces lint + clippy + tests on every push and PR.
- The rest of this document explains what all of that means, and where the gaps are.

## 2. Primer: what Stow and Tuckr are, and where rustow sits

**GNU Stow** is a small Perl program that has been the reference tool for dotfile symlinking for ~30 years. You keep each app's config files in a directory ("package", e.g. `Configs/zsh/`), and Stow creates symlinks from the target tree (usually `$HOME`) back into the package. The hard parts are:

- **Tree folding** — instead of creating dozens of links under `~/.config/eza/`, Stow creates ONE symlink `~/.config/eza -> Configs/eza/.config/eza`. Faster, cleaner, fewer links.
- **Unfolding** — if another package suddenly needs to own one file inside that folded directory, Stow splits the fold symlink back into a real directory and links each file individually.
- **Conflict detection** — if `~/.zshrc` already exists as a real file, Stow stops and does nothing rather than overwriting it. (Modern Stow ≥2.0 plans everything before touching the disk.)
- **Unstowing** — deleting the links a package created.

**Tuckr** is a newer Rust rewrite of the same idea, with extra machinery on top: host-specific "profiles", conditional deployment per OS, pre/post-deploy hooks, secret management, and a TUI-ish add flow. If you want a dotfiles *framework*, that is the bigger tool.

**rustow** is a narrow, safe Stow-compatible linker in Rust. It keeps the parts above that are universal (folding, refolding, conflicts-never-silently-overwritten, stowrc migration compat) and leaves out both Stow's vintage baggage (dot-name mangling, compat mode, regex conflict policy) and Tuckr's framework scope (profiles, hooks, secrets).

### Vocabulary, in plain words

- **Package** — a top-level directory under your `source` root holding one app's files, e.g. `Configs/zsh/`.
- **Source directory** — the root of all packages (`Configs/`). rustow calls this `--dir` / `DOTFILES_DIR` / `source`.
- **Target directory** — where links are created, usually `$HOME`. `--target` / `DOTFILES_TARGET` / `target`.
- **Linking** — creating symlinks in the target pointing into the package. **Unlinking** — deleting only the links that package created.
- **Fold** — replacing a would-be tree of links with a single symlink (see above). A directory is folded only when the target has no real directory there and nothing ignored (like a nested `.git`) lives inside the subtree.
- **Unfold** — splitting a rustow/stow-owned fold link into a real directory so two packages can coexist under it.
- **Refold** — after unlinking, collapsing a directory that now holds only links into one package back into a single fold symlink.
- **Conflict** — the target path is occupied by something rustow would have to replace: a real file, a real directory, or a symlink pointing into a different package. rustow never resolves one implicitly; either you pick an action (overwrite / adopt / skip / interactive merge) or the whole run aborts before any file is created or deleted.
- **Adopt** (`--adopt`) — move the existing target file *into* the package, then link. (stow `--adopt`.)
- **Dry run** (`-n`) — print what would happen, change nothing.
- **Two-phase plan** — rustow first computes every action and every conflict in memory; if any conflict is unresolved, ZERO filesystem changes happen. No half-applied states.
- **Ownership** — a symlink is "rustow-owned" if it resolves into the configured `source` tree. Foreign links are never removed without an explicit flag.
- **Provenance** — where the effective config came from (CLI flag / env var / config file / stowrc), tracked so rustow can explain itself on startup.
- **`clean`** — deleting rustow-owned symlinks whose *destination no longer exists* (the equivalent of `stow -c`). Distinct from unlink: unlink removes a package's links unconditionally; clean removes only broken ones, and works even if the package was deleted entirely.
- **`fold_ignore`** — config list of package names that must never be folded (they get per-file links while everything else folds as usual).
- **Ignored paths** — rustow ships Stow's default ignore list (`.git`, editor backups, etc.) plus your own `ignore` globs in `config.toml`. Ignored paths block folding (so nested `.git` directories are never swallowed into a fold) and are never linked.

## 3. What changed since the last report (v0.1.1, unreleased)

- **`rustow clean`** — sweeps the target tree for rustow-owned symlinks whose destination no longer exists (fold links included), deletes them, re-folds candidates. `-n` reports without deleting; foreign symlinks are never touched; verbose output (`-v`) prints each one. Adding this closed the last functional gap versus `stow -c`.
- **`fold_ignore`** — per-package fold opt-out in `config.toml` (e.g. one app that must always get per-file links) instead of disabling folding globally.
- **`--no-stowrc` / `RUSTOW_NO_STOWRC=1`** — kill switch for the `~/.stowrc` fallback. See §6.4 for why this lives on the CLI and in the environment rather than in `config.toml`.
- **`source == target` refusal** — rustow now refuses to link a package tree onto itself with a clear error, instead of doing undefined things to your files.
- **11 new edge-case tests** (`tests/edge_cases.rs`): non-ASCII package/path round-trip, `fold = false`, dir named `0`, unlink of never-linked/empty packages, source==target refusal, clean idempotency and fold-removal, stowrc kill-switch. These are CLI-level, tempdir fixtures only.
- Test count went 126 → **149**.

## 4. What rustow covers today (by capability, not by file)

For each capability: what it does, and how it is exercised in tests. "Tested black-box" means through the real binary against tempdirs; "planner-tested" means the conflict/fold logic is asserted at the plan layer; both are first-class.

### 4.1 Linking and folding

- `rustow sync` links every package; `rustow link <pkg>...` links selected ones. Tested end-to-end via the CLI.
- Tree folding: a package whose target subtree doesn't exist yet gets one symlink for the whole directory. Tested (fold creation, demotion when the subtree contains ignored paths, stale-fold replacement).
- Unfold: a rustow-owned fold link colliding with another package's real directory is split into a real directory and both packages are re-linked. Tested.
- Refold: unlinking a directory that now contains only links into one package collapses it back into a fold symlink. Tested.
- Cross-package same-run claims are pre-computed so fold decisions don't misfire. Tested.
- `fold = false` (global) forces per-file links; `fold_ignore = [...]` opts specific packages out. Tested (both).
- Re-linking is idempotent; dangling links pointing back into the package are repaired. Tested.
- Packages containing only ignored paths are a clean no-op. Tested.
- Foreign symlinks and real files are never silently replaced; `-f` and `--adopt` are the two explicit escape hatches. Tested.

### 4.2 Unlinking

- `unlink <pkg>...` (aliases `remove`, `rm`) removes only that package's links; unrelated real files and foreign links in the same tree are left alone. Tested, including foreign-symlink preservation.
- `reset` unlinks everything. Tested end-to-end.
- `relink` unlinks then re-links. Tested.
- Unlink of a package that was never linked, or is empty, is a successful no-op. Tested (this report's new batch).
- `clean` deletes only broken rustow-owned links. Tested (live links untouched, dry-run, foreign-broken links kept, fold links whose package vanished, idempotency).

### 4.3 Conflict handling

- Detected before any mutation: real file at target, real directory at target, symlink to another package, symlink to nowhere-into-the-package, wrong-package links, dir-vs-file shape mismatches. All abort the entire run when unresolved. Tested at plan and CLI level.
- Resolution paths: interactive prompt on a TTY (skip / overwrite / adopt / interactive merge in a diff tool), `-f` to overwrite everything, `--adopt` to absorb everything, non-TTY without a flag → abort with a full report and zero changes. Tested for every non-interactive path.
- The interactive merge flow (open diff tool on target vs package file, then link) is wired and reviewed, but has **no automated TTY test** — see §5.2.

### 4.4 Adopting existing files

- `create <app>` (alias `add`) moves existing target paths into a new package and links them, in one confirmed operation. Handles `--source` (custom path), `--path` (package-relative destination), `--empty`, `--yes` (non-interactive), absolute/traversal path rejection, cross-filesystem moves, and refuses to touch an existing package's contents without confirmation. Tested.

### 4.5 Status and observability

- `status [pkg]...` reports per-package `linked` / `partial` / `unlinked` / `conflict` with a table, `-s` summary mode, `-v`/`-vv` per-issue detail (line-capped; `-vv` uncaps), `--state` filtering (repeatable, also applies to JSON), and `--json` machine-readable output. Tested, including exit codes (0 iff every inspected package is fully linked) and `--json` parseability.

### 4.6 Configuration and provenance

- `~/.config/rustow/config.toml`: `source` (**required, no default** — rustow refuses to guess), `target` (default `$HOME`), `fold`, `fold_ignore`, `ignore`, `diff_tool`, `verbose`.
- Precedence: CLI flags > environment (`DOTFILES_DIR`, `DOTFILES_TARGET`) > `config.toml` > `~/.stowrc` (fallback only when no config file exists).
- `~/.stowrc` supports `--dir` / `--target` / `--verbose` with stow-compatible expansion: `$HOME`, `${HOME}`, leading `~`, and backslash escapes (`\$`, `\~`) keeping things literal. stowrc can be disabled outright with `--no-stowrc` or `RUSTOW_NO_STOWRC=1`; when that happens and a stowrc file exists, rustow prints a one-line note instead of silently ignoring it.
- Typos and unknown keys in config warn; unknown stowrc keys warn and are ignored; malformed stowrc lines abort with line numbers. Tested.
- On a TTY with no config, rustow warns and offers to create one pre-filled from the values in use; `[s]ilence` writes a stamp file; `[a]bort` exits. Non-TTY with no config: a one-line warning on stderr, never a prompt, and the run continues (a conflict needing a decision still aborts the link phase as usual). Tested at the suite level.
- `source == target` is refused. Tested.
- `schema.json` and `docs/config.toml` are mechanically checked against the config model by tests — they cannot drift silently.
- Exit codes (documented in the spec now): `0` OK, `1` conflicts/unhealthy/other errors, `2` user aborted.

### 4.7 Distribution

- Tagged releases cut binaries for linux gnu/musl (x86_64, arm64), macOS (x86_64, arm64), Windows (x86_64, arm64) via GitHub Releases. No crates.io.
- `cargo install --path .` works; binary is self-contained (no runtime).

## 5. What is missing, what is partial

### 5.1 Missing

- **Property-based planner tests.** The planner has several interacting invariants (fold/unfold/refold, cross-package claims, ignore handling, dangling-link repair) asserted case-by-case but never randomized. For a tool that mutates your home directory this is the single most valuable test investment available.
- **TTY interaction tests.** Every conflict test runs non-interactively (via `-f`, `--adopt`, abort, or planner-level calls). The interactive prompt — choose skip/overwrite/adopt/merge, the merge flow into a diff tool — has no automated coverage. `expect`-style harness would work; nothing is wired up.
- **`status --json` schema is not versioned.** Scripts consuming the JSON cannot rely on it across releases. Needs a `version` field or equivalent.
- **Exit-code semantics are now documented (§4.6) but not all pinned by tests** — e.g. nothing asserts code `2` for a user-aborted conflict.
- **`target` inside `source`** (and vice versa) is not refused — only strict equality is. Stow does the same check only for the equality case as well; the broader containment case is undecided.

### 5.2 Partial

- **Conflict-resolution UX** — non-interactive paths exhaustively tested; interactive prompt flow reviewed but untested end-to-end.
- **Windows** — symlink creation requires Developer Mode or admin; CI covers the binary building and Linux behavior; interactive Windows symlink semantics are not pinned in tests.
- **Verbose output for link/unlink commands** — covered indirectly; no assertion pins the exact verbose format for those paths yet.

### 5.3 Honest limitations of this report

- Coverage is inventoried by hand, not measured with `cargo llvm-cov`. "Tested" means a named behavior has at least one assertion somewhere in the suite; line/branch percentages are unknown.
- No performance benchmark exists. rustow is fast enough for dotfiles; nothing is measured.

## 6. The specific questions that came up — answered

These were raised against the previous version of this report. Context first, then the honest answer.

### 6.1 "You say the cleanup linking is missing — don't we have `rustow clean`?"

Yes. `clean` (added 2026-11-13, unreleased) is exactly the GNU Stow `-c` equivalent: it walks the target tree, finds symlinks rustow owns that now resolve into nothing, and deletes them. The previous report predated it. Fold links whose package vanished are handled, `-n` gives a dry run, and foreign links — even broken ones outside the source tree — are left alone.

### 6.2 "What are `defer` and `compat`? Should we implement them?"

Both are GNU Stow flags; neither exists in rustow today.

**`--defer=<regex>`**: skip linking a file whose path matches the regex, if another package already owns it. Think "this package loses to whoever already claimed that path". Example: `stow --defer=man zsh` leaves existing man pages linked to whichever package got there first. **`--override=<regex>`** is the opposite: always link matching paths even if another package owns them, overwriting those links.

rustow has no regex-scoped conflict policy. The equivalent behaviors are: `-f` (overwrite **everything** that conflicts), `--adopt` (absorb **everything**), or the interactive prompt (decide per conflict). What rustow does **not** have is "these specific path classes defer to another package" — e.g. "package `perl` owns `man/` and `info/`; any package I link there must defer."

Should it be implemented? **Recommendation: no, not in V1.** Three reasons: (1) the use case is narrow — it exists for sites where one stow repo manages software whose man pages collide; dotfile repos rarely have colliding path classes beyond what whole-package conflicts already catch; (2) regex conflict policy is a power feature whose misuse silently links or overwrites the wrong things — the exact failure mode the two-phase plan exists to prevent; (3) if it ever becomes necessary, the right shape is a per-package conflict policy in `config.toml` (same shape as `fold_ignore`), not a raw regex CLI flag. If you want to reconsider, say so — it is roughly a day of work: a `defer` list per package, planner consultation at conflict time, three tests.

**`--compat`** (`-p`): when unstowing, scan the *whole target tree* instead of just the directories the package image mentions. Stow 2.x has this as a legacy fallback for orphaned links — links whose files disappeared from the package, which the default package-walk cannot find.

**Recommendation: do not add a `--compat` flag. `rustow clean` already does this job better**: it walks the target tree independently of any package image and removes every rustow-owned link whose destination is missing — strictly more general than compat, and it doesn't couple unlink semantics to tree walking. If an orphan sweep is wanted, `clean` is the command and its docs say so.

### 6.3 "Should we add a local ignore file like Stow's?"

Stow supports two ignore-list files:

- **`.stow-local-ignore`** — in the package's top-level directory; a list of regexes. Any file or directory in that package matching any entry is never stowed. The file is always ignored itself.
- **`~/.stow-global-ignore`** — same thing, user-wide; used only when the package has no local list; otherwise Stow's built-in default list is used.

They solve a real problem: "this one package contains files I never want linked" (build artifacts, READMEs, nested tool state).

rustow's current answer: built-in default ignore list + `ignore` globs in `config.toml` (global) + `fold_ignore` for the fold-only case. It deliberately has **no per-package ignore files**, because two mechanisms (dotfiles inside packages vs. central config) split one decision across two locations and surprise people.

Should one be added? **Recommendation: no — but keep the door open with a config-table extension, not dotfiles.** If a real need shows up, the coherent shape is a `[package.foo]` table in `config.toml` with its own `ignore` (mirroring `fold_ignore`), keeping one source of truth and no hidden dotfiles peppered through packages. The cost of the dotfile version is low to implement, but the maintenance and surprise costs are real, and Stow's own manual admits the design is tolerated rather than loved. Adding it "for compatibility" would import Stow's wart wholesale; adding a config table is honest work and can wait for a concrete need.

`~/.stow-global-ignore` itself is fully redundant with `ignore` in `config.toml` — the same capability, one mechanism, no glob/regex split. No action.

### 6.4 "Add an option to disable `.stowrc` detection, even with no config or env vars."

Done, with one deliberate design call worth spelling out.

A `config.toml` key (e.g. `stowrc = false`) **cannot** work in the scenario you describe — by the time a config file exists, stowrc is already never consulted. Adding a key that does nothing would be a fake option: present in the schema, absent from every code path, lying to the next reader of the config reference.

So the kill switch lives in the two places that *can* work with zero config and zero env vars:

- **`--no-stowrc`** (global CLI flag), and
- **`RUSTOW_NO_STOWRC=1`** (environment variable, matching the existing `DOTFILES_DIR`/`DOTFILES_TARGET` pattern).

Either one disables stowrc detection completely. When rustow would have read a stowrc but was told not to, it prints a one-line note naming the file (`ignoring ~/.stowrc (disabled by --no-stowrc / RUSTOW_NO_STOWRC)`) instead of surprising silence. With no config and no env vars and stowrc disabled, you get the standard "source is not set — run `rustow config init`" error, exactly as if the stowrc never existed.

If you want the schema key anyway, it is three lines — say the word; but it would be inert by construction.

### 6.5 "The report mapped Stow/Tuckr files to rustow files — I don't memorize either codebase. Tell me what we cover and what we don't."

That mapping is gone. §4 lists capabilities covered, §5 lists what is missing or partial, §6.2–6.4 cover the open questions, and nothing in this document requires knowing Stow's or Tuckr's file layout. Where Stow/Tuckr knowledge is genuinely needed you get the definition inline (see §6.2, §6.3), not a pointer.

### 6.6 "Make this project for anyone, not for this machine or this person."

All framing implying a sole intended environment was removed. rustow is documented as a general Stow-compatible linker; decisions are justified on their merits (safety, surprise factor, maintenance cost), not on what one setup happens to need. Where a scope boundary exists (no profiles, no hooks, etc.), it is stated as a design decision of the tool, not as someone's preference.

### 6.7 "Context. I'm not a Stow expert."

This document now opens with a primer (§2), defines every term on first use (§2 → Vocabulary), and explains every referenced Stow feature before judging it (§6.2, §6.3). If any section still assumes knowledge you don't have, that's a defect — say which one and it gets rewritten.

### 6.8 "Add tests for everything we already support, focused on edge and failing cases."

Done as far as the cheap, high-value cases go — 11 new tests in `tests/edge_cases.rs` (§3): non-ASCII paths/packages, `fold = false`, dir named `0`, unlink no-ops, source==target refusal, clean fold/idempotency, stowrc kill switch. This also *caught and fixed two bad assumptions in this very report* (fold semantics land at the missing-dir boundary; `fold = false` had zero coverage until now).

Deliberately **not** done (see §5.1 for why each is a larger investment): property-based planner tests, TTY interaction tests, JSON schema versioning, deeper verbose-format assertions. Those are listed as the next work items, in order.

## 7. Deliberately out of scope, and why

These are design decisions of the tool, stated so adopters can plan around them.

- **`dot-` name mangling (`--dotfiles`)**. Stow renames `dot-bashrc` → `.bashrc` so package trees can be browsable without hidden files. rustow links literal trees; package files are exactly what lands in the target. The convention saves nothing in a modern repo layout and doubles the mental model.
- **Defer/override regexes**. See §6.2. Superseded by `-f`, `--adopt`, interactive resolution, and (prospectively) per-path conflict policy in config.
- **Compat mode**. See §6.2. Superseded by `clean`.
- **`.stow-local-ignore` / `.stow-global-ignore`**. See §6.3. Redundant with `ignore` globs; per-package version would be a config table if ever needed.
- **Profiles / host-conditional deployment / root targeting**. rustow manages "this source tree → this target tree, once". Host switching is a namespace problem with many existing solutions; bolting one on would multiply every code path (planner, status, create) by profile.
- **Hooks (pre/post deploy)**. Deploy automation belongs to your actual deploy pipeline, not a linker. Combining them makes failures un-debuggable ("did the link or the hook fail?").
- **Secrets / encryption**. Different category of tool problem (key management, rotation); using a linker to deliver secrets conflates the threat models.
- **`stow -c`-adjacent archive modes, `from-stow`**. Migration is a one-shot manual affair; supporting bulk converters is feature debt with no steady-state payoff.
- **Property tests** are *not* out of scope — they are missing (§5.1), and recommended as the next investment.

## 10. Glossary (for stow refugees and newcomers alike)

- **Package** — one app's directory of config files inside your source tree.
- **Source tree** — the directory holding all packages. **Target tree** — where links go (usually `$HOME`).
- **Fold** — one directory → one symlink. **Unfold** — split that symlink back into a real directory. **Refold** — collapse a links-only directory back into a symlink.
- **Two-phase** — everything planned in memory before anything touches disk; unresolved conflicts abort the whole run.
- **Conflict** — target occupied by something rustow must not silently replace.
- **Adopt** — move the target file into the package, then link it.
- **`clean`** — remove broken rustow-owned symlinks (`stow -c`).
- **Provenance** — which config layer supplied the settings in effect.
- **`fold_ignore`** — packages that never fold.
- **Idempotent** — running link twice changes nothing the second time.
